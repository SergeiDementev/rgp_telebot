# Telegram RPG — контекст проекта

Текстовая пошаговая RPG в Telegram-боте. Сейчас проект — только дизайн-документация в `docs/` (кода ещё нет, реализация не начата). Здесь — сжатая выжимка из `docs/`, чтобы не перечитывать все документы заново. При реальных вопросах по деталям и формулам всегда сверяйся с первоисточником в `docs/`, этот файл — только карта и краткое содержание.

## Идея игры

Герой перемещается по локации, ищет противников, дерётся по пошаговой боевой системе на кубиках, получает победные очки за победу, прокачивает характеристики. MVP — чистый PvE, одна локация, три противника (мышь/волк/кабан). PvP заложено в архитектуру, но не реализуется в MVP.

Ключевая метафора: бой должен ощущаться как "игра по переписке" — каждое нажатие игрока = осязаемый бросок кубика с видимым числом, а не пассивное чтение готового отчёта.

## Сквозные архитектурные принципы

- **Клиент-серверная архитектура.** Telegram-бот — тонкий клиент. Вся игровая логика и вычисления — на HTTP-бэкенде. Бот не хранит и не считает ничего игрового (ни HP, ни броски, ни урон) — только инициирует запрос и показывает готовый результат сервера. Причины: простота и честность (нельзя подменить результат на клиенте).
- **`core/` — чистые функции без зависимостей** от HTTP/БД/Telegram. Тестируется и симулируется независимо.
- **Пошаговая обработка.** Один HTTP-запрос = один ход. Состояние боя хранится в БД между запросами, не в памяти вызова. Нужно для симметрии PvE/PvP (в PvP второй игрок может отвечать спустя часы) и для будущего усложнения хода без переделки архитектуры.
- **Единая механика PvE и PvP** — боевое ядро не знает, кто (игрок или бот-ИИ) управляет стороной, разница только в том, кто инициирует следующий шаг.
- **Рендеринг отделён от логики.** `core/` считает структурированные факты → БД хранит факты (не готовый текст) → `api/rendering.py` превращает факты в текст → бот только показывает. Даёт переносимость на другой фронтенд/язык без изменений в игровой логике.
- **Все правила объясняются один раз, через `/rules`.** Экраны игры и бой — лаконичные, без встроенных пояснений/подсказок.

## Характеристики персонажа

| Стат | Природа | Роль |
|---|---|---|
| **HP** | Независимый ресурс | Уменьшается от урона. 0 — поражение. |
| **Здоровье (vitality)** | Прокачиваемый стат | `HP_max = 20 + Здоровье × 10`. Не влияет на скорость регенерации HP. |
| **Сила (STR)** | Детерминированный рычаг | Определяет силу удара, единственная полностью предсказуемая характеристика. |
| **Ловкость (AGI)** | Элемент случая | Вероятность полного уворота (бинарно: 0 урона либо весь урон). Не мастерство, а "стихийная удача тела". |
| **Удача (LUCK)** | Редкие благоприятные развилки | Двойной удар (§5) и возможность побега при критичном HP (§6). |

Формулы кубиков — в `combat_mechanics.md` §3-6:
- Атака (d10): 1-2 промах, 3-5 фикс. 50% силы, 6-10 линейный рост 60→100%.
- Уворот: количество "успешных" граней d10 растёт по кривой насыщения от Ловкости (MIN_FACES=1 всегда, MAX_FACES/K — черновые константы для калибровки).
- Двойной удар: асимптотическая (не достигающая 100%) кривая от Удачи, `floor()`, отдельная от уворота пара MIN/MAX/K.
- Побег по HP-порогу: отдельный независимый бросок Удачи, не общий с двойным ударом.

## Механика побега (§7) и обстоятельства (§8)

- Побег — не бесплатный выход, а ставка: один безответный удар преследователя без защиты убегающего. Если добивает — поражение убегающего; если выживает — `player_fled`/`enemy_fled`, награды нет в любом случае.
- В начале боя выбор "принять/отступить" доступен **всегда**, безусловно, независимо от исхода обстоятельства (сложность попавшегося моба сама по себе достаточная причина).
- В процессе боя (по HP-порогу) — возможность выбора открывается только успешным броском Удачи; право сгорает только при отказе после успешного броска (при провале самого броска — сохраняется).
- Бот всегда выбирает бежать, если у него открылась возможность.
- Обстоятельство (d10 сразу после инициативы, кидает победитель инициативы): 20% debuff / 60% ничего / 20% buff кидающему, модификатор ×1.2/×0.8 к Силе на весь бой. Полярность относительна к кидающему.

## Полный порядок одного боя (§9, кратко)

```
1. Инициатива (обе стороны).
2. Обстоятельство (сторона-победитель инициативы) → модификатор Силы на бой.
3. Игроку всегда предлагается выбор: принять бой / отступить (безответный удар, §7).
ЦИКЛ ХОДОВ (пока HP одной из сторон не станет 0), ход атакующего A, защищающийся B:
  4. Если HP(A) ≤ порог побега и право не использовано → бросок Удачи на побег (§6) → выбор.
  5. Бросок Удачи на двойной удар (§5) → 1 или 2 удара.
  6. На каждый удар: атака (Сила) → если не промах, уворот (Ловкость) → урон → если HP(B)≤0, бой окончен.
  7. Ход переходит другой стороне, повтор с шага 4.
```

Исходы (§10): `victory` (полная награда), `defeat`, `player_fled`, `enemy_fled` (без награды).

## Игровой цикл вокруг боя (`gameplay_loop_mvp.md`)

- `/start` — приветствие, не создаёт персонажа. `/rules` — единственное место с полным объяснением механик. Никнейм — из Telegram, без отдельного ввода.
- Создание персонажа — гибрид: фикс. база (Здоровье=3, Сила=3, Ловкость=3, Удача=1) + пул очков (5) распределяется вручную, тем же интерфейсом, что и левел-ап. Нераспределённые очки не сгорают, переносятся в `unspent_stat_points`.
- Прокачка — по 1 очку за клик, мгновенно, без отмены. Кнопки "+1" исчезают, когда очков нет (не становятся серыми).
- Уровни: победные очки копятся навсегда (не тратятся), при пересечении порога — +1 очко прокачки. Порог растёт: `threshold(N) = threshold(N-1) + 10×N`.
- Поиск противника — d10: 1-6 мышь (60%), 7-9 волк (30%), 10 кабан (10%). Награды (черновые): мышь=1, волк=5, кабан=15 победных очков. Поражение/побег не наказываются и не откатывают прогресс.
- Регенерация HP — ленивый пересчёт по времени (`hp_current`, `last_hp_update_at`), без фоновых процессов/таймеров. `REGEN_PER_SECOND = 1` фиксировано, стат Здоровье влияет только на `hp_max`. Пересчёт происходит при любом обращении к серверу.
- Экраны боя редактируют одно сообщение (`editMessageText`) внутри боя; финальный итог боя — новое сообщение. Любой бросок кубика в тексте показывает число: `<число> → <результат>`. Раунд разбит на 2 нажатия: "Атаковать" (фаза игрока) и "Защищаться" (фаза противника).

## Архитектура бэкенда (`backend_plan.md`)

- **Стек:** Python + FastAPI, SQLite + SQLAlchemy (миграция на Postgres — смена строки подключения), бот на aiogram, HTTP-клиент бота — httpx.
- **Структура:** `core/` (combat.py, progression.py, circumstance.py — чистая логика) → `api/` (routers: character/encounter/combat, schemas/, rendering.py, dependencies.py) → `db/` (models.py, session.py, migrations/) → `content/enemies.json` (статы мобов) → `scripts/simulate_combat.py` (калибровка) → `bot/` (handlers, client.py).
- **Модели БД:** `Character` (статы, `victory_points`, `unspent_stat_points`, `hp_current`+`last_hp_update_at` для регенерации), `CombatSession` (стороны, статус, `result`, модификаторы Силы от обстоятельства, `flee_opportunity_used` — живёт в сессии, не в персонаже, сгорает только в рамках одного боя, `turn_log` JSON).
- **Эндпоинты:** `POST /character`, `GET /character/{id}`, `POST /character/{id}/allocate_point`, `POST /encounter/search` (сразу бросает инициативу+обстоятельство), `POST /combat/{id}/confirm` (fight/flee), `POST /combat/{id}/turn`, `POST /combat/{id}/flee_decision`, `GET /combat/{id}`. Клиент никогда не шлёт сырые броски/урон — только решения (fight/flee/continue, какой стат качать).
- **Рендеринг:** `core/combat.py` считает факты → `turn_log` в БД хранит факты (не текст) → `api/rendering.py` превращает факты в текст на лету при формировании ответа. Позволяет добавить второй фронтенд/локализацию без изменений в `core/`.
- **Авторизация бот↔API** для MVP — статический ключ в заголовке `X-Internal-Api-Key`.

## Открытые вопросы / черновые параметры

Требуют калибровки на плейтесте, не блокируют реализацию (полный список — `combat_mechanics.md` §11 и `gameplay_loop_mvp.md` §10):
- `MAX_FACES`, `K` для уворота; `K` для двойного удара; `MIN_FACES/MAX_FACES/K` для побега — все независимы друг от друга.
- `flee_threshold_percent` (черновой 25%), `modifier_percent` обстоятельства (черновой 20%).
- Стартовые значения статов, пропорции поиска противника (60/30/10), награды по мобам (1/5/15), константа роста уровней (10), `REGEN_PER_SECOND` (1) — все черновые.
- Статы конкретных мобов (мышь/волк/кабан) — не определены, результат этапа 2.
- Идемпотентность запросов на ход — отложена до PvP.
- PvP целиком — обсуждён на уровне принципов, не оформлен отдельным документом, не входит в MVP.
