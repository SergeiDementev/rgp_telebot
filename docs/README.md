## 1. Идея игры

Простая текстовая RPG в формате Telegram-бота. Герой перемещается по локациям, ищет противников, сражается по пошаговой боевой системе на основе кубика, получает награду за победу и прокачивает характеристики. Чистый PvE на одной локации с тремя рядовыми противниками и финальным боссом. PvP решено не делать — игра остаётся однопользовательской.

**Ключевая метафора, которой подчинена вся боевая механика:** бой должен ощущаться как игра по переписке — каждое действие игрока буквально бросает кубик и сразу видит результат, а не читает готовый отчёт о случившемся.

## 2. Запуск

Нужны два процесса одновременно: HTTP-бэкенд (`api/`) и Telegram-бот (`bot/`). Бэкенд можно запускать и тестировать отдельно, бот без запущенного бэкенда работать не будет.

**1. Зависимости**

Требуется Python 3.14 (та же версия, что и в `Dockerfile` — не зафиксирована через `pyproject.toml`/`runtime.txt`, только здесь и в самом образе).

```
pip install -r requirements.txt
```

Для тестов и разработки дополнительно:

```
pip install -r requirements-dev.txt
```

**2. Настройка `.env`**

Скопировать `.env.example` в `.env` и заполнить:

```
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
API_BASE_URL=http://127.0.0.1:8000
INTERNAL_API_KEY=dev-local-key
DATABASE_URL=postgresql+psycopg2://rpg:rpg@localhost:5432/rpg
```

`DATABASE_URL` — необязательна: без неё `db/session.py` использует локальный SQLite-файл (`rpg.db`), без какой-либо настройки. Для PostgreSQL нужен запущенный сервер — быстрее всего поднять один контейнер (без docker-compose, это отдельный шаг для развёртывания на сервере):

```
docker run -d --name rpg-postgres -e POSTGRES_USER=rpg -e POSTGRES_PASSWORD=rpg -e POSTGRES_DB=rpg -p 5432:5432 -v rpg_pgdata:/var/lib/postgresql/data postgres:16
```

**3. Применить миграции БД**

```
alembic upgrade head
```

Создаёт (или доращивает) схему в БД, на которую указывает `DATABASE_URL` (SQLite или PostgreSQL — миграции одинаковы для обеих, docs/backend_plan.md §10). Нужно один раз при первом запуске и заново после каждой новой миграции — само приложение схему БД больше не создаёт и не трогает.

**4. Запустить бэкенд**

```
uvicorn api.main:app --reload
```

Swagger-документация эндпоинтов — на `http://127.0.0.1:8000/docs`.

**5. Запустить бота** (в отдельном терминале, при запущенном бэкенде)

```
python -m bot.main
```

**6. Тесты**

```
python -m pytest tests/
```

### Через Docker (альтернатива шагам 1-5 выше — для переноса на сервер)

Всё (api, бот, PostgreSQL) — одним `docker-compose.yml` (docs/notes.md, п.63). Шаг 2 (`.env`) всё равно нужен — `TELEGRAM_BOT_TOKEN`/`INTERNAL_API_KEY`/`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` берутся оттуда; `API_BASE_URL`/`DATABASE_URL` для контейнеров заданы прямо в `docker-compose.yml` (имена сервисов сети compose, не `localhost`).

**На чистом хосте (первый раз, без предыдущего шага 2 выше) нужен ещё именованный volume** — `docker-compose.yml` подключает `rpg_pgdata` как `external: true` (переиспользует тот же volume, что и ручной `docker run` из шага 2, если он уже был), поэтому compose его не создаёт сам и упадёт с ошибкой, если volume не существует:

```
docker volume create rpg_pgdata
```

Дальше — обычный запуск:

```
docker compose up -d --build
```

Поднимает Postgres, применяет `alembic upgrade head` при каждом старте api-контейнера (идемпотентно) и запускает бэкенд + бота. Бэкенд публикуется на `http://127.0.0.1:8000` (как и при ручном запуске), у бота портов нет — он только исходящий (long-polling).

```
docker compose ps               # статус/health всех трёх сервисов
docker compose logs -f          # логи всех сервисов
docker compose up -d --build    # пересобрать образ и перезапустить после изменений в коде
docker compose down             # остановить (том rpg_pgdata с данными не удаляется)
```

Тесты через Docker не гоняются — `pytest` по-прежнему только на хосте (шаг 6 выше), контейнеры этого не касаются.

**Логи бота на диске** (docs/notes.md) — `bot/` пишет `logs/bot.log` (плюс ротация `logs/bot.log.1`/`.2`/`.3`) в дополнение к обычному выводу в stdout (`docker compose logs bot`), через bind mount `./logs:/app/logs` в `docker-compose.yml` — переживает `docker compose up -d --build`, в отличие от вывода контейнера. Директория `logs/` создаётся автоматически при первом запуске, в `.gitignore`/`.dockerignore`.

**Бэкап БД** — `db/backup_db.sh` (docs/notes.md): `pg_dump` из контейнера `db` → gzip → загрузка в Oracle Object Storage (`--auth instance_principal`, без ключей на диске) → ротация бэкапов старше 7 дней. Пишет в `logs/backup.log`. На сервере — cron пользователя `ubuntu`, 00:00 UTC; вручную — `db/backup_db.sh` из любой директории.

## 3. Архитектурные принципы (сквозные, действуют на весь проект)

- **Клиент-серверная архитектура.** Telegram-бот — тонкий клиент, вся игровая логика и вычисления — на HTTP-бэкенде. Бот не хранит и не считает ничего игрового, только инициирует запросы и отображает готовый результат.
- **`core/` — чистые функции без зависимостей.** Ядро игровой логики (бой, прогрессия) не знает про HTTP, БД, Telegram. Тестируется и симулируется независимо.
- **Пошаговая обработка.** Один HTTP-запрос = один шаг/ход. Состояние живёт в БД между запросами, не в памяти одного вызова.
- **Боевое ядро не различает, кто управляет стороной.** Игрок или AI-логика моба/босса — разница только в том, кто инициирует следующий шаг (`core/combat_mechanics.py` работает одинаково для обеих сторон). PvP решено не делать (игра остаётся однопользовательской PvE), это просто следствие того, как устроено ядро, не задел под будущую фичу.
- **Рендеринг текста отделён от логики.** `core/` считает структурированные факты (какие грани выпали, какой урон) → БД хранит факты → отдельный слой (`api/rendering.py`) превращает факты в готовый текст → бот только показывает. Это сохраняет переносимость на другой фронтенд/язык без изменений в игровой логике.
- **Все правила объясняются один раз, через кнопку "📜 Правила".** Не команда (`/rules` убрана, docs/notes.md п.1 — отдельным сообщением она рвала очередь с редактируемым боевым сообщением) — кнопка на экране статов, ведёт на меню разделов (`content/rules.md`, парсится `bot/rules_content.py`). Сами экраны игры не содержат пояснений и подсказок — предполагается, что игрок уже ознакомлен с механикой.

## 5. Характеристики персонажа — очень кратко

| Стат | Роль |
|---|---|
| **HP** | Независимый ресурс. 0 — поражение. |
| **Здоровье** | Прокачиваемый стат, определяет `HP_max`. Не влияет на скорость регенерации. |
| **Сила** | Детерминированный урон. Единственная полностью предсказуемая характеристика. |
| **Ловкость** | Вероятность полного уворота от удара. Элемент случая, не мастерства. |
| **Удача** | Двойной удар и возможность побега при критичном HP. Редкие благоприятные развилки. |

Подробности и формулы — в `combat_mechanics.md`, §2-7.

## 6. Игровой цикл — очень кратко

```
/start → 📜 Правила (опционально) → Начать игру (создание персонажа, гибрид: база + пул очков)
  → Экран статов
  → Искать противника (бросок d10, пропорции зависят от уровня — 60/30/10 мышь/волк/кабан на 1-2 уровне, к 9-10 уровню зеркально 10/30/60)
  → Определить инициативу + обстоятельство → Вступить в бой / Отступить
  → Цикл раундов: Атаковать / Защищаться (каждое нажатие — бросок(и) кубика с видимым числом)
  → Завершение боя (победа / поражение / побег) → награда (только при победе)
  → Регенерация HP — ленивый пересчёт по времени, без фоновых процессов
  → Экран статов → снова "Искать противника" или "Меню игрока" (статы/прокачка + золото/лут/зелья)
```

**`/reset`** (или кнопка "🗑 Обнулить персонажа" в "Меню игрока") — необратимо архивирует текущего персонажа и сразу показывает экран создания нового, через подтверждение (кроме экрана победы над боссом, там кнопка уже сама по себе осознанное решение). История прошлого прохождения не удаляется физически, остаётся в БД для аналитики (docs/notes.md, п.41).

Полные макеты экранов — в `gameplay_loop_mvp.md`, §9.
