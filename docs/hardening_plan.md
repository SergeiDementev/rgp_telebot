## Как работать по этому плану

- **Правила проекта — в `CLAUDE.md` rpg_tele_bot:** любое действие с внешним эффектом (создание и изменение файлов, коммиты, ветки, запуск кода) — только после подтверждения автора. Сначала описать, что будет сделано, потом делать.
- **Перед началом** прочитать `CLAUDE.md`, `docs/README.md`, `docs/backend_plan.md` и `docs/notes.md` — там решения и история проекта. План не отменяет их: если пункт плана противоречит записанному решению, сначала обсудить с автором.
- **Этапы — по одному, в своей ветке, с pull request.** В конце этапа: все тесты зелёные, документы соответствуют сделанному, короткий итог автору — что сделано, что проверить руками.
- **Автор — QA, Python знает, но многие инструменты для него новые.** Объяснять решения простыми словами, термины расшифровывать.
- **Сервер — общий с «Быками и коровами».** Действия на сервере — только с подтверждения автора. Не трогать: папку `/home/ubuntu/bulls_and_cows`, его контейнеры (`bulls-and-cows-*`), порты 80, 443 и `127.0.0.1:3001`, строку cron в 00:30 UTC, бакет `bulls-and-cows-backups`. Никаких `docker system prune`, удаления «неиспользуемых» томов и остановки всех контейнеров.
- **Секреты** (`.env`, токен бота, пароли, `INTERNAL_API_KEY`) не выводить на экран и не писать в чат.

## Этап 1. Автоматические проверки

**Цель:** ни один красный код не попадает в `main`.

1. `pyproject.toml` с настройками **ruff** (линтер и форматировщик) и **mypy** (проверка типов). Начать мягко: mypy строго — для `core/`, обычный режим — для остального; не пытаться исправить всё за раз. `db/models.py` написан в старом стиле SQLAlchemy (`Column(...)`, не `Mapped[...]`/`mapped_column()`) — без этого mypy не увидит типы атрибутов `Character`/`CombatSession` вообще; решить отдельно, ставить ли плагин `sqlalchemy[mypy]` или переписать модели на новый стиль (это один файл, не весь проект).
2. Отформатировать код ruff одним отдельным коммитом (чтобы в истории было видно: «только форматирование»).
3. Исправить ошибки линтера и типов, которые найдутся. Спорные места — показать автору.
4. **GitHub Actions** (`.github/workflows/ci.yml`) на pull request и на push в `main`: ruff, mypy, pytest.
5. Тесты API — ещё и на PostgreSQL: в CI поднять PostgreSQL (service container), схему создавать **миграциями Alembic**, а не `create_all`. Так проверяются и сами миграции. Если часть тестов завязана на SQLite — обсудить с автором, оставлять ли быстрый прогон на SQLite рядом.
6. Образ PostgreSQL в CI брать из зеркала `public.ecr.aws/docker/library/postgres:16` — у Docker Hub лимит скачиваний для GitHub Actions.

**Готово, когда:** в PR видны зелёные проверки ruff, mypy и pytest на PostgreSQL; README описывает, как запустить их локально.

## Этап 2. Нет настройки — не запускаемся

**Цель:** ошибка в настройках видна сразу при старте, а не через час или никогда.

1. Убрать `DEV_DEFAULT_API_KEY`. Настройки API и бота — через **pydantic-settings**: проверяются при старте, без обязательной настройки сервис падает с понятным сообщением.
2. Убрать SQLite по умолчанию из `db/session.py`. Для разработки — PostgreSQL в Docker (например, `docker compose up db` или отдельный `docker-compose.dev.yml`). Обновить README и `.env.example`.
3. В Compose обязательные переменные — с `${VAR:?}`: без них Compose не запустится.
4. Тесты: без `INTERNAL_API_KEY` API не стартует; неверный ключ — `401`.

**Важно для сервера:** перед выкладкой убедиться, что в серверном `.env` есть все обязательные переменные (проверять наличием и длиной, не выводя значения). Иначе после обновления API не поднимется.

## Этап 3. Эксплуатация

**Цель:** сервер не переполнится логами, а из копии точно можно восстановиться.

1. **Ротация логов Docker** для всех сервисов: `logging: driver json-file, max-size 10m, max-file 5` — общим блоком (якорь YAML), как в `docker/docker-compose.prod.yml` «Быков и коров». Это защищает и соседний проект на той же ВМ.
2. **`db/restore_db.sh`:** без аргументов — список копий в бакете; с именем копии — скачать, остановить бота и API, восстановить базу, поднять сервисы, проверить здоровье. Перед восстановлением — явное подтверждение («база будет заменена»).
3. **Проверка восстановления на сервере** (с подтверждения автора, по шагам): свежая копия → автор делает действие в игре, которого не будет после восстановления → восстановление → автор видит состояние на момент копии. Результат — в `docs/notes.md`.
4. Неймспейс Object Storage — из `.env` (`OCI_NAMESPACE`), а не из скрипта; в `.env.example` — пустая строка с комментарием.
5. Закрепить версию образа PostgreSQL точнее (`postgres:16-…` с конкретной версией) — чтобы обновление базы было решением, а не случайностью при пересборке.

**Готово, когда:** восстановление проверено на сервере, логи контейнеров ротируются (`docker inspect` показывает настройки логов).

## Этап 4. Коды ошибок и рефакторинг роутеров

**Цель:** логику боя можно проверять без HTTP, а клиент понимает ошибки без разбора текста.

1. **Закрытый список кодов ошибок** (например, `character.not_found`, `combat.not_your_session`, `stats.no_points`) в схемах API. Ответ с ошибкой — `{"error": {"code": "...", "details": {...}}}`. Бот выбирает текст по коду.
2. Тест на каждый код: «этот код воспроизводится настоящим запросом и приходит с правильным статусом».
3. **Рефакторинг роутеров** (например, `api/services/` или просто разбить `api/routers/combat.py` на несколько файлов поменьше): роутер принимает запрос, вызывает общую обработку и правила из `core/`, сохраняет, возвращает JSON. Боевая логика уже живёт в `core/` (`docs/backend_plan.md`) — цель здесь не "вынести утечку", а снизить размер/число ответственностей одного файла и выделить повторяющиеся куски (обработка 409/404, построение ответа).
4. **Случайность — параметром:** генератор (`random.Random`) передаётся в сценарии через зависимость FastAPI; тесты задают его с известной последовательностью вместо подмены `random.randint` в модулях.
5. **Константы формул — в одном месте** (`core/`), их используют и API, и симуляции.
6. **Ограничения в базе** миграцией: `CHECK` там, где у значения есть границы (уровни, очки, здоровье), уникальность там, где она подразумевается (один активный персонаж на игрока — частичный уникальный индекс).
7. **`Character.welcome_message_id`/`main_message_id`** — перенести в отдельную таблицу бота (миграция с переносом данных), чтобы таблица персонажей описывала только игру. Подтверждено автором отдельно от Mini App (см. статус выше) — самостоятельная чистка, не часть Этапа 5.

Делать по одному роутеру за раз; поведение для игрока не меняется — это проверяют существующие тесты.
